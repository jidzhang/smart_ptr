Code Review: smart_ptr_mt
Overall it's a well-structured, clearly-commented portable smart pointer library. However, there are some real bugs, a few serious design problems, and some portability concerns worth fixing before production use.

🔴 Critical Bug — Double-Free Race in release() (line 382–385)
This is the most serious issue. The control block deletion check is not atomic:
cppif (0 == counter->get_ref_count() && 0 == counter->get_weak_ref_count())
{
    delete counter;  // ← RACE: two threads can both pass this
}
get_ref_count() and get_weak_ref_count() are two separate atomic reads. Thread A (last strong ref) and Thread B (last weak ref) can each read both as 0 and both call delete counter — a double-free and heap corruption.
Standard fix: use the "extra weak ref" trick — initialize m_weak_ref_count to 1 instead of 0, representing the strong group. When the strong count reaches 0, call dec_weak_ref() there. Only delete the counter when dec_weak_ref() returns 0. This guarantees exactly one thread deletes the counter.
cpp// In ref_count constructor:
ref_count() : m_strong_ref_count(1), m_weak_ref_count(1) {}  // ← weak starts at 1

// In release(), strong path:
if (0 == counter->dec_ref())
{
    mem_mgr::deallocate(m_ptr);
    if (0 == counter->dec_weak_ref())  // drop the "strong group" weak ref
        delete counter;
}
else if (!is_strong)
{
    if (0 == counter->dec_weak_ref())
        delete counter;
}

🔴 Critical — m_counter and m_ptr are Public (line 327–328)
cpp    ref_count* m_counter;   // ← public!
    T*         m_ptr;       // ← public!
protected:
    ...
The protected: label appears after these two members, making them public. Any external code can corrupt the ref count. The cast functions (static_pointer_cast etc.) abuse this intentionally — they should instead be declared friend. Move the protected: above m_counter.

🟠 Serious — shared_ptr(const weak_ptr&) Does Not Throw on Expiry (line 478)
cppexplicit shared_ptr(const weak_ptr<Q, mem_mgr2>& rhs) : baseClass(rhs) {}
acquire() silently returns an empty shared_ptr if the weak ptr is expired. The standard std::shared_ptr constructor from weak_ptr throws std::bad_weak_ptr. This silent failure makes bugs hard to find. At minimum, document this divergence clearly; ideally add an assertion or throw.

🟠 Serious — Unnecessary virtual Destructor in base_ptr (line 232)
cppvirtual ~base_ptr() { release(); }
There is no use-case for holding a base_ptr* polymorphically. This vtable pointer adds 8 bytes per instance on 64-bit platforms and forces a vtable. Remove virtual — the subclass destructors are all empty anyway, so release() called from base_ptr::~base_ptr() is sufficient.

🟡 Portability — Reserved Identifier as Header Guard (line 5)
cpp#ifndef __SMART_PTR_H__
Identifiers beginning with __ (double underscore) are reserved by the C++ standard. This can cause subtle conflicts on some compilers/standard libraries. Rename to:
cpp#ifndef SMART_PTR_MT_H_INCLUDED

🟡 Portability — operator->() Asymmetry Between Windows and GCC (line 258–267)
On Windows, operator->() always returns _NoAddRefReleaseOnComPtr<T>* — even for completely non-COM types. On GCC it returns plain T*. This means debug builds of non-COM code on Windows produce different pointer types than on GCC. The COM suppression wrapper should only be applied when actually using com_mem_mgr, not globally.

🟡 Portability — SMART_PTR_NOEXCEPT on Move Assignment is Incorrect (line 462–473)
cppshared_ptr& operator=(shared_ptr&& rhs) SMART_PTR_NOEXCEPT
{
    this->release();  // ← calls mem_mgr::deallocate(), which CAN throw
    ...
}
If deallocate() throws (e.g. a custom mem_mgr), this violates the noexcept contract and calls std::terminate(). Either document that custom mem_mgr::deallocate() must be noexcept, or remove SMART_PTR_NOEXCEPT from move assignment.

🟡 VS2005 Specific — _MSC_VER C++11 Detection
VS2005 = _MSC_VER 1400, VS2008 = 1500, VS2010 = 1600. The C++11 gate _MSC_VER >= 1900 correctly targets VS2015+. However, VS2010 (1600) does support rvalue references — SMART_PTR_SUPPORT_MOVE could be enabled for it with:
cpp#if __cplusplus >= 201103L || _MSC_VER >= 1600
#define SMART_PTR_SUPPORT_MOVE 1
But noexcept requires VS2015+, so keep SMART_PTR_NOEXCEPT gated at >= 1900. Worth considering if VS2010 move semantics are desired.

🔵 Design Notes
#Issue1array_mem_mgr::allocate(int n) is declared but never called — shared_array always takes a raw pointer. Can be removed to avoid confusion.2make_shared allocates object and control block separately. std::make_shared fuses them in one allocation for better cache locality and fewer new calls. Fine to leave as-is for older compilers, but worth a comment.3default_delete<T[]> is defined but unique_ptr<T[]> won't automatically use it — a user creating unique_ptr<int[]> still gets std_mem_mgr (which calls delete, not delete[]). Consider a partial specialization of unique_ptr for array types, or a clear comment warning users to pass array_mem_mgr explicitly.4get_ref_count() uses InterlockedCompareExchange(..., 0, 0) on Windows as an atomic read — correct, but a no-op CAS is a heavy fence. On VS2005+ you could use InterlockedExchangeAdd(..., 0) which is lighter, though either is correct.
